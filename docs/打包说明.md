# 打包说明

把 Alcove 打成**免安装的文件夹版（onedir）**，Windows 上双击 `Alcove.exe` 就能用。
Linux 也会顺带出一个产物，主要用途是我这边验证。

## 为什么必须在 Windows 上打包

PyInstaller **不支持交叉编译**（官方文档原话是「在你想要支持的每个系统上各跑一次」）。
在 Linux 上 `python -m PyInstaller Alcove.spec` 只会得到 Linux 的 ELF 可执行文件，
改后缀成 `.exe` 是没用的。本机没装 wine，所以 **Windows 的 exe 只能在 Windows 上构建** ——
这就是走 GitHub Actions 的原因（`MAWHA/Alcove` 是公开仓库，Actions 额度不限）。

## 怎么拿到 exe

**手动触发（最常用）**：GitHub 仓库 → `Actions` → 左侧「打包」→ `Run workflow` → 选 `main` → 跑。
大约 6~10 分钟后，在这一页底部的 `Artifacts` 里下载 **`Alcove-windows-x64.zip`**。

**打 tag 自动发 Release**：`git tag v0.1.0 && git push origin v0.1.0`，
除了 artifact，还会自动挂到 Releases 页面上。

**在本地 Windows 上自己打**：见下面「本地构建」。

下完解压，目录长这样：

```
Alcove/
├── Alcove.exe            ← 双击它（或命令行 Alcove.exe --gui）
└── _internal/            ← 别删、别改名，exe 全靠它
```

## 产物里装了什么

| 东西 | 从哪来 | 为什么 |
| --- | --- | --- |
| `assets/` | 仓库 | 模板图 238 张 + 两套 OCR 模型 + 旧 pipeline JSON |
| `MaaAgentBinary/` | `maaagentbinary` 包 | maafw 连设备时找的 `minitouch`/`maatouch`/`minicap` |
| `maa/bin/*` | `maafw` 包 | MaaFramework 的一整套原生库（框架/工具包/控制单元/OCR） |
| `flet_desktop/app/` | GitHub Releases | flet 的桌面端客户端（约 40MB），预置进去就不用运行时联网下 |
| `config/` | 仓库 | maafw 的 schema 与 `maa_option.json` |
| `PyPipeline/Tasks` 等 | 仓库源码 | 这几个目录是**扫目录**加载的，源码必须躺在盘上 |

## spec 里几个不显然的决定

`Alcove.spec` 里每一段都写了注释，这里只列「不看注释会想不通」的五条：

### 1. 只读的东西和可写的东西必须分家

源代码运行时，「程序目录」和「可写目录」是同一个（仓库根）。打包之后就分开了：

* 只读 → `sys._MEIPASS`（即 `_internal/`），在 Program Files 里是**不可写**的；
* 可写 → exe 旁边；exe 旁边也写不了就退到 `%LOCALAPPDATA%/Alcove`，再不行退到 `%TEMP%/Alcove`。

`MWATools/MWAPaths.py` 用 `sys.frozen` 判断并把这两件事分别导出成
`PROJECT_ROOT` / `BUNDLE_ROOT` / `USER_ROOT` / `ASSETS_DIR` / `CONFIG_DIR` / `LOG_DIR`。
**新代码要写文件，一律用 `USER_ROOT` 系，别用 `PROJECT_ROOT`。**

### 2. `MaaAgentBinary/` 必须和 `maa/` 平级

它是 `maaagentbinary` 这个包**写在 site-packages 顶层的裸数据目录**，没有 `__init__.py`
（`import maaagentbinary` 会报 `ModuleNotFoundError`），PyInstaller 不会自动收。
而 `maa/controller.py` 是按 `os.path.dirname(maa.__file__) + "/../MaaAgentBinary"` 找的 ——
所以 spec 里单独手工收了一份，dest 写死 `MaaAgentBinary`。

少了它的后果：连设备时回落到 ADB 截图/输入，慢一个数量级（Waydroid 上实测只剩 adb）。

### 3. flet 的桌面端客户端要预置

`flet-desktop` **PyPI 包是空壳**（`py3-none-any`，0.01MB，只有三个 .py），
真正的客户端二进制在 GitHub Releases 上（Windows 版 `flet-windows.zip` 约 38MB）。
`flet_desktop.ensure_client_cached()` 会先找包里的 `flet_desktop/app/<压缩包>`，
找不到就**联网下载**到 `~/.flet/client/`。

`scripts/fetch_flet_client.py` 负责在打包前把压缩包塞进 `flet_desktop/app/`，
这样打出来的包离线也能跑。另外 `flet-cli` 必须装 —— 它用 entry point
（`[pyinstaller40] hook-dirs`）注册了官方 PyInstaller hook，没装这个 hook 不生效。

### 4. maa 里「按名字 dlopen」的库，要在包根再放一份

这是我在 Linux 产物上踩到的真坑，Windows 同理（`LoadLibrary`）：

* `collect_all("maa")` 把 `maa/bin/*.so|*.dll` 收进 `_internal/maa/bin/`；
* PyInstaller 的 bootloader 会把 `_internal` 塞进动态库搜索路径，于是
  `libMaaUtils.so` 这种**被 DT_NEEDED 依赖**的库是**从包根**加载的；
* maa 的 C++ 层用 `dladdr()`/`GetModuleFileName` 反推自己的目录 → 算出来是**包根**；
* 可框架是用 `dlopen`/`LoadLibrary` **按名字**加载控制单元的（`MaaAdbControlUnit` 这些），
  DT_NEEDED 的库 PyInstaller 会自动搬到包根，**dlopen 的不会** →
  包根里没有它们 → 报 `Failed to load library […/MaaAdbControlUnit]`，
  `--list` 里一个 ADB 设备都扫不到。

所以 spec 第 4b 段把文件名里带 `ControlUnit` / `AgentClient` / `AgentServer` 的库
再往包根放一份（加 `plugins/`），代价约 2MB。**这一段不能删。**

### 5. 扫目录加载的包要「源码 + hiddenimports」双份

`PyPipeline/Tasks`、`PyPipeline/CustomActions`、`PyPipeline/CustomRecos` 三个目录，
和 `MWATools`、`MWAGui` 一样，都是运行时用 `pkgutil.iter_modules()` 扫出来的
（`Tasks/__init__.py` 的 `load_all()`、`MWACustomAction.py` 的 `_scan()`）。
PyInstaller 的静态分析看不到这种导入，所以 spec 里两边都要做：
`datas` 把 `.py` 源码原样放进包（`iter_modules` 读的是磁盘），
`hiddenimports` 用 `collect_submodules()` 把它们编进 PYZ。

**以后新增任务模块不用改 spec**（在 `PyPipeline/Tasks/` 下就是自动的）。

## 辅助脚本

```bash
python scripts/fetch_ocr_models.py    # 下载两套 OCR 模型（不在版本库里，约 40MB）
python scripts/fetch_flet_client.py   # 预置 flet 桌面端客户端（约 40MB）
python scripts/prune_dist.py          # 打完包收尾：删掉 hook 塞进来的重复目录 + 报体积
```

第一个是**必须**的：`assets/*/base/model/ocr/` 被 `.gitignore` 忽略，clone 下来是空的。
spec 里对此有预警（不会中断构建，只是打出来的包识别不了文字）。

## 体积

Linux onedir 实测 **256MB**（压缩后约 100MB），构成大致是：

| 项 | 体积 |
| --- | --- |
| `maa/`（含 bin 里整套原生库） | 67M |
| 包根的 maa 动态库副本（见第 4 条） | 25M |
| `assets/`（两套资源包，OCR 模型占 41M） | 52M |
| `numpy` + `numpy.libs` | 41M |
| `MaaAgentBinary` | 14M |
| `pillow` + `pillow.libs` | 18M |
| `flet_desktop`（桌面端压缩包） | 16M |

想瘦身可以考虑：① 只留 `assets/resource_picli`（省 25M，但上游代码要用另一套）；
② 设 `MAAFW_BINARY_PATH` 指向包根、去掉 `_internal/maa/bin`（省 67M，但依赖这个环境变量、
属未验证路径）。目前都**没做**。

## 本地构建

```bash
# 1) 依赖（用 uv 或 pip 都行）
uv sync --extra gui          # 或： pip install "maafw>=5.14.3" pillow pyyaml strenum flet flet-desktop
pip install flet-cli pyinstaller

# 2) 资源
python scripts/fetch_ocr_models.py
python scripts/fetch_flet_client.py

# 3) 打包
python -m PyInstaller --noconfirm --clean Alcove.spec
python scripts/prune_dist.py

# 4) 冒烟
dist/Alcove/Alcove --help    # Windows 是 dist\Alcove\Alcove.exe --help
```

## 排错

**第一步永远是 `Alcove.exe --selftest`** —— 它不连设备，把「路径分家有没有生效、
资源包在不在、OCR 模型全不全、扫目录加载的模块收没收进去」挨个查一遍并打印结果，
失败时直接告诉你哪一项缺了。

| 现象 | 原因 |
| --- | --- |
| 启动就报 `model file not found` | OCR 模型没下载，跑 `scripts/fetch_ocr_models.py` |
| 界面卡在 `working…` 很久 | 设备扫描是阻塞的 C 调用，GUI 已改成后台线程 + 25 秒超时；超时后点「刷新」重试 |
| `--list` 里找不到任何 ADB 设备 | ① 设备确实没连上；② 控制单元没打进包 —— 见「第 4 条」 |
| 连上设备但截图/点击很慢 | `MaaAgentBinary/` 没进包，回落到了 ADB 输入 —— 见「第 2 条」 |
| 点「开始」时弹出安装提示 / 长时间没反应 | `flet_desktop/app/` 里没有桌面端压缩包，运行时在联网下载 —— 见「第 3 条」 |
| 日志乱码 | 已内置 `_force_utf8_console()`；不管用时设 `PYTHONUTF8=1` |
| 写文件报 `Permission denied` | 用了 `PROJECT_ROOT` 而不是 `USER_ROOT` —— 见「第 1 条」 |
